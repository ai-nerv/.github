Memory

Writing must never stall a turn. Reading must never be trusted blindly. And what a request holds is the memory layer's decision, made fresh before every one.

plate 06out, in, and back again

Out: handed over before it is needed

A session is behind a mutex and a commit is a short lock, so what is committed is handed to a writer and the turn carries on. Before the next request is laid out, magi waits for that handover to land — balthasar cannot lay out what it has not been told. If it never lands, the entry is still in the conversation; only the durable record is lost.

In: nothing is trusted blindly

The memory slot of each layout holds what this prompt calls for, chosen once per prompt — a prompt that is only “ok, go on” keeps the last one's, byte for byte. Each memory is presented for what it is:

Something you said once in March is not something true now. Flattening the two would present an old remark as a standing fact, so the hedge is kept rather than the memory dropped — the model can still use it, and is told how much to trust it.

Rules, notes and the catalog

After a turn, a helper may be handed the job of drawing notes from it. A note becomes a rule — sent on the user's channel — only when it matches a complete instruction a person actually gave, word for word, negations and conditions kept; anything paraphrased, quoted or said by another agent stays an observation, lower trust. Every change is recorded and can be undone, and with balthasar.memory.review on, each one waits for your approval. The catalog lists what the project holds as true, one line each, and says whether that is all of it — so a model can tell nothing is held about this from the search missed it.

Two claims that cannot both be true are linked rather than one quietly winning: balthasar disagreements lists them, and balthasar settle says which is right. A rule a person later takes back is not recalled again, and neither is what it had cited.

Back: did it help

A turn may report what it used and how that went, and balthasar keeps the ledger — off by default, on with balthasar.outcome = { capture = true }. The harness reports the event; it does not claim a match it did not verify, which would be asserting an analysis rather than reporting what happened.

→ {"call":"used","args":["inject-1788683868-e3b0c442",{"tool":"shell","action":"…"}]}
← {"ok":true,"family":1,"n":1,"result":[{"action":"use-1788683868-inject-17886"}]}
→ {"call":"outcome","args":["use-1788683868-inject-17886",{"kind":"succeeded"}]}

Without it a memory layer can rank by recency and by similarity, and never by whether anything it offered was any use.

Which store a directory gets

plate 07walk up until something claims it

A store somebody made deliberately wins first; then the checkout the directory is in. Five worktrees of one project share one memory rather than starting each other's amnesia.

Both walks stop before a directory nobody owns. Without a ceiling, one stray marker high up collects everything beneath it — and both kinds occur naturally: a leftover store in the temporary directory, and a .git at $HOME, which is what an ordinary dotfiles repository is. Either would put unrelated projects into a single memory. The rule is stricter for the inferred marker than the deliberate one: a repository at $HOME is not the project a subdirectory belongs to, while a store somebody explicitly created there is.

Resuming

With balthasar running there is no journal on disk at all — it is the store, and a second copy is a copy that goes stale. magi --resume asks balthasar which runs this project has had and replays the newest.

$ magi -p "remember the number 8231, just say ok"
ok
$ magi --resume -p "what number did I ask you to remember?"
8231

A separate process, after the first one and the balthasar it started are both gone. What survives is the store, not a running thing. --resume-run <id> carries on a particular run rather than the newest — how a script hands work from one invocation to the next.

The program holding it is whatever fills the memory role — balthasar unless magi.memory names another. --resume needs only the role’s core: sessions to find the newest run, replay to read it back. Both wait for a store that is still opening, rather than resuming into an empty conversation.
